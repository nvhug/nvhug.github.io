# Contract: `ai_usage_report` RPC + `ai_usage_log` read access

The page consumes exactly two interfaces. Both are admin-gated by RLS, so a non-admin caller
receives no data rather than an error that reveals the data exists.

---

## 1. `ai_usage_report(p_from, p_to, p_user)` — every aggregate, one snapshot

```
ai_usage_report(
  p_from  timestamptz,
  p_to    timestamptz,
  p_user  uuid DEFAULT NULL,
  p_scope text DEFAULT 'all'   -- 'all' | 'user' | 'deleted' | 'system'
) RETURNS jsonb
```

Called as `supabase.rpc('ai_usage_report', { p_from, p_to, p_user, p_scope })`.

**`p_scope` selects the drill-down, and `p_user` only means anything when it is `'user'`.**
`p_user` alone cannot express these: `NULL` already means "unscoped", so there is no value
that means "the deleted accounts". A caller that sends `p_user: null` for that drill-down
receives the **global** report and, if it labels the view as filtered, shows one group's
spend as the whole product's.

| `p_scope` | Rows included |
|---|---|
| `all` | everything in the period (`p_user` ignored) |
| `user` | one live account, named by `p_user` |
| `deleted` | every deleted account, as one group — `user_id IS NULL AND actor = 'user'` |
| `system` | scheduled jobs — `actor = 'system'` |

An unrecognised scope returns the empty-period shape rather than widening to everything:
it fails closed, in the direction that cannot leak.

**Changing this argument list changed the function's signature.** `CREATE OR REPLACE` does
not replace a function whose parameter list differs — it creates a second one, and every
call then fails as ambiguous. The migration therefore drops the three-argument version
first, and the `GRANT` names the four-argument signature.
Bounds are half-open: `created_at >= p_from AND created_at < p_to`, so consecutive periods
neither overlap nor drop a row on the boundary.

**`p_to` is required and must be pinned by the caller.** The function must not default it to
`now()`, and no caller may recompute it. The client computes `p_from`/`p_to` once per render or
filter change, holds them in state, and passes the same values to this RPC **and** to the raw-log
query below. This is what makes guarantee 1 hold across both — the RPC alone cannot, because the
log is a second query.

All token field names match the `ai_usage_log` column names exactly, in the aggregates and in the
raw-log projection alike, so there is only one spelling of each concept to get right.

### Response shape

```jsonc

    "reasoning_tokens": 14300,  // subset of output_tokens, never added to a total

    "unpriced_calls": 3,        // rows whose cost_usd IS NULL
    "unpriced_models": ["deepseek-chat"],
    "active_users":   7,        // distinct user_id, excluding actor='system'
```

### Guarantees the caller may rely on

1. **One snapshot.** Every array and the summary are computed in one function body over one
   read of the table. `summary.cost_usd` therefore equals the sum of `cost_usd` across
   `by_surface`, across `by_model`, across `by_user`, and across `daily`, for the same
   arguments (SC-003). Callers must not recompute the summary from a breakdown — but if they
   did, the figures would agree. **This extends to the raw log only when the caller reuses the
   same pinned `p_to`** — the log is a separate query and nothing in this function can bound it.
2. **`daily` is dense.** One element per calendar day in `[p_from, p_to)` in
   `Asia/Ho_Chi_Minh`, ascending, including days with no usage (all counts `0`, `cost_usd`
   `0`). Generated by `generate_series` and left-joined, so the caller never reconstructs
   missing days (FR-021).
3. **Breakdowns are ordered by `cost_usd DESC NULLS LAST`**, so a row with only unpriced calls
   sorts last rather than to the top as a NULL.
4. **`cost_usd` sums exclude unpriced rows, and `unpriced_calls` counts them.** Both numbers are
   always present. The UI must render the cost as a lower bound whenever
   `unpriced_calls > 0` (FR-010a) — the sum alone is not the total.
   `summary.unpriced_models` names the offending models so the message can say which price is
   missing.
5. **`cached_input_tokens` is a subset of `input_tokens`, never an addition.** A total is
   `input_tokens + output_tokens` (FR-002a). No field named `total_tokens` is returned, so
   there is nothing to double-count.
6. **`by_user` distinguishes three kinds** (FR-007a), grouped by `(user_id, actor)`:
   - `actor = 'user'`, `user_id` non-null → a live account. One row each. Resolve the display
     name separately against `user_profiles`; a missing profile row is a data inconsistency and
     renders as a short id, **not** as a deleted account.
   - `actor = 'user'`, `user_id` null → **all deleted accounts, as one aggregated row.** Because
     `ON DELETE SET NULL` destroys the identity, per-deleted-account attribution is impossible by
     construction and this row is the sum of every deleted account's spend. Intended — see the
     plan's R5 for why the alternative (snapshotting an identity onto each row) was rejected on
     privacy grounds. Drill down into it with `p_scope: 'deleted'`.
   - `actor = 'system'` → a scheduled job. One aggregated row, excluded from
     `summary.active_users`. Drill down with `p_scope: 'system'` — "which feature is the
     cron spending on" is a real question, even though "what is this person doing" is not.
7. **`failed_calls` and `failed_cost_usd` are provided but no tile renders them.** FR-016 defines
   exactly four tiles, and neither is one of them. They exist so that FR-005a's "wasted spend is
   readable as the summed cost of failed entries" is answerable from this one response instead of
   a second query, and so the log's failed-row treatment has a total to sit against. A caller may
   ignore both without losing anything the spec requires.
8. **Empty period.** Every array is `[]` except `daily`, which is still dense with zero rows.
   The summary's numerics are `0` and `unpriced_models` is `[]`. Never `null`, never an error —
   an empty period is a valid answer (FR-025).

### Bounds are clamped, and an invalid range is not an error

- **`p_to` must be greater than `p_from`.** An inverted or zero-length range returns the
  empty-period shape (guarantee 8), not an error and not a `daily` of `[]`-with-no-days.
  Stated because a chart computing `width / daily.length` over an empty array renders `NaN`.
- **The window is clamped to 400 days.** The longest period the UI offers is 90, so this is far
  above real use and still finite. Without it `daily` is generated from the *arguments*, and a
  caller could ask for a millennium.

### Access

`SECURITY INVOKER`, and the function's first CTE evaluates `public.is_admin()`. Everything else
derives from that CTE, so a non-admin caller produces zero rows at the first step and the
function does **no work at all** before returning the empty-period shape.

That ordering is the point. The RLS policy below gates *rows*, and the `daily` series is built
from the arguments rather than from the table — so RLS alone would let any authenticated
account, including one `proxy.ts` denies the page to, ask for a thousand-year window and make
the database materialise millions of objects. Returning zeros after doing that work is not a
denial. Doing no work is.

Display names are **not** joined in. `user_id` is returned raw and resolved against
`user_profiles` by the caller, so this function needs no access to profile data.

## 2. `ai_usage_log` — the raw log, read directly

The paginated call log is an ordinary select, not an RPC — no aggregation is involved:

```ts
supabase
  .from('ai_usage_log')
  .select('id, user_id, actor, surface, provider, model, input_tokens, ' +
          'cached_input_tokens, output_tokens, reasoning_tokens, cost_usd, outcome, created_at',
          { count: 'exact' })
  .gte('created_at', from)
  .lt('created_at', to)
  .order('created_at', { ascending: false })
  .range(offset, offset + pageSize - 1)
```

Add `.eq('user_id', userId)` when a drill-down is active.

- The same pinned `from` / `to` as the RPC call must be used here, or the log can include a row
  the aggregates did not see (guarantee 1).
- `pricing_version` is deliberately not selected — it exists for audit, not display (FR-011a).
- Ordering is `created_at DESC`. Two rows written in the same millisecond (the two horoscope
  palace batches, the two food-photo stages) can tie; `id` is the tiebreaker so paging stays
  stable and no row appears on two pages (FR-022).
- `cost_usd` arrives as `null` for an unpriced row. The UI must render that as unknown, never
  as `0` (FR-010).
- No column in this projection can carry prompt or response text, because no such column
  exists (FR-014a).

### RLS

```sql
-- read: admins only
FOR SELECT USING (public.is_admin())
-- write: nobody, from any browser client
FOR ALL USING (false)
```

Inserts happen exclusively through the service-role client from the six server routes.

## 3. What the recording side must uphold

Not a callable interface, but the contract the six call sites share. `logAiUsage()` in
`src/lib/ai-usage.ts` is the only writer.

| Rule | Requirement |
|---|---|
| One entry per **provider call**, not per user action | FR-001a |
| Output tokens include billed reasoning: Gemini adds `thoughtsTokenCount`, DeepSeek does not re-add `reasoning_tokens` | plan R2 |
| `logAiUsage` is awaited under its own ~1s timeout, never fire-and-forget, never unbounded | plan R7 |
| `model` is what the provider says it served, falling back to what was asked | FR-003 |
| A recording failure is swallowed to `console.error` and never propagates | FR-004 |
| Failed calls are recorded, and a failure does not zero the cost | FR-005, FR-005a |
| Cost and `pricing_version` are computed at write time, never on read | FR-011, FR-011a |
| An unknown model writes `NULL` cost, never `0` | FR-010 |
| `actor = 'system'` when there is no signed-in initiator | FR-007 |
| No prompt or response content, not even truncated | FR-014a |
